# Gemini 視覺辨識 v0（2026-11-20）

狀態：團隊決定網頁只用 Google Gemini 的免費 API 辨識食物。YOLO 和 Claude 的方法先放棄，程式保留在 repo 裡
（`src/detection/model.py`、`src/detection/claude_vision.py` 與它們的測試），網頁上不再顯示。
程式：`src/detection/gemini_vision.py`；網頁：`src/ui/app.py`；測試：`tests/test_gemini_vision.py`（用假的 client，不連網）。

核心原則不變：**Recipe candidates may explain hidden calories, but are not visual proof.** Gemini 只回報照片裡看得到的東西。

## 1. 流程

1. 使用者上傳照片，勾「我了解並同意把這張照片傳給 Google Gemini 辨識」，按「開始辨識」。
2. 程式先在本機自動找學生證（`card_locator.py`），找到的話，在**要送出的那份**照片上把卡片塗成灰色，卡號不會送出。
3. 照片縮到長邊 1568 px，重新存成 JPEG（只有像素，沒有 EXIF 和 GPS）後送出。
4. 回答用 JSON schema 限制格式。每道菜回傳：
   - 繁體中文名稱、英文名稱
   - 已知的食物代碼，或 `other`
   - 盤裝或碗裝
   - Gemini 慣用的 `box_2d`：[ymin, xmin, ymax, xmax]，0–1000
   - 看得到的食材、把握程度
5. 網頁顯示藍框 G1、G2…，接著是粗估份量區（`rough_volume_estimation_v0.md`）：
   - 學生證比例尺
   - 排除認錯的菜、手動加菜
   - 自己填重量

## 2. 模型與金鑰

- **模型**：先列出這把金鑰能用的模型，依序試 **Flash Lite**（新到舊），再試 **Flash**（新到舊）。
  上次成功的模型排第一，記在 Git 忽略的 `data/gemini_state.json`，網頁重開也記得。
  - 遇到找不到（404）、額度用完（429）、太忙或超時（503／504），就換下一個。
  - 每個模型最多等 30 秒，整體最多 75 秒，超過就提示「Gemini 免費版現在太忙」。
  - 思考程度設低：Gemini 3.x 用 `thinking_level=LOW`，2.x 用 `thinking_budget=0`。
- **免費額度**（2026-11-20 在 AI Studio「Rate Limit」頁面看到的，每個模型分開計算）：
  - Flash 系列：每分鐘 5 次、每天 20 次。
  - Flash Lite 系列：每分鐘 15 次、每天 500 次。
  - `gemini-2.5-flash` 已不開放給新用戶（404）。
- **為什麼 Flash Lite 排第一**（2026-11-20 實測）：
  - Gemini 3.8／3.7／3.6／3.5 Flash 常回 503／504，簡單請求也要等超過 25 秒。
  - 3.6 Flash 有時會成功，要 12–37 秒。
  - 3.5 Flash Lite 只要 3–9 秒。
- **連線方式**：Gemini API（AI Studio 金鑰）。Vertex AI express mode 不接受這種金鑰，已經拿掉。
- **金鑰位置**：寫在 `FoodCal_AI/.streamlit/secrets.toml` 的 `GEMINI_API_KEY = "..."`，或設定環境變數 `GEMINI_API_KEY`。
  這個檔案不會被加進 Git，金鑰不要貼進對話、程式碼或文件。
- **使用者自己的金鑰**（2026-11-26）：網頁的「開始辨識」卡片有密碼欄位，使用者可以貼自己的 AI Studio 金鑰。
  有填就優先用它，沒填才用上面的共用金鑰；網頁沒有共用金鑰時這格必填。詳細見 `docs/demo_ui_v0.md`「使用自己的 Gemini API 金鑰」。
- **錯誤提示**：金鑰無效、超過免費額度（429）、被安全機制擋下、回答被截斷或格式錯誤，都有中文說明。

## 3. 免費版的條款（使用前要知道）

- Google 的 Gemini API 條款規定，免費版送出的內容和回答，Google 可以用來改進產品。這些內容會先去識別化，之後可能由真人審閱。
- Google 建議不要送出敏感或個人資料；台灣使用者適用這套免費條款。
- 所以網頁會：
  1. 在同意文字裡寫明以上條款。
  2. 送出前先塗掉學生證。
  3. 提醒使用者不要拍到人臉。
- 免費額度依專案計算，有每分鐘、每天的次數上限，確切數字在 Google AI Studio 查看。超過時網頁會提示稍後再試。

## 6. 飲料、水果與整顆食物（2026-11-26）

辨識指令（`instructions()`）和 schema 加了：

- `container`：多了 `cup`，給杯子、玻璃杯、瓶子裡的飲料，框杯口（俯視看到的口緣）。
- `shape`：多了 `whole`，給一整顆或還帶皮的東西（整根香蕉、整顆蘋果或柳丁、饅頭、玉米、帶皮的西瓜片）。
- 飲料的成分：
  - 看得到的冰塊算 `ice`，珍珠算 `tapioca_pearls`。
  - 手搖店的奶茶算 `milk_tea`（奶精），標「鮮奶」的才算 `fresh_milk_tea`。
- 飲料的 `cooking_method` 是甜度：
  - 杯子貼紙或標籤讀得到時，用 全糖／少糖／半糖／微糖／無糖。
  - 讀不到甜度的手搖飲用 `drink_sugar_unknown`。
  - 白開水、鮮奶、黑咖啡用 `none`，生的水果也是 `none`。
- 新的食材代碼和 7 種飲料的 `food_key` 都由程式自動列進指令（`INGREDIENTS`、`COOKING_METHODS`、`FOOD_TEMPLATES`）。
- 甜度和熱量的算法見 `docs/nutrition_model_v0.md` 第 7 節。這次沒有用真的飲料照片測 Gemini；第一次實測時，要確認它會不會讀貼紙。

## 9. 逐一食材辨識（2026-11-26）

使用者的意見：Gemini 應該辨識照片裡的**食材**（白飯、雞肉、豆腐、蛋…），不是整道菜；食材名稱可以冠上料理方式（照燒雞、白切雞），
這樣份量比較準；料理方式再從整道菜的食譜去找。

- **為什麼份量會比較準**：份量是「框的面積 × 厚度 × 密度」。以前一道照燒雞腿飯只有一個框，白飯和雞肉用同一個厚度、平均密度；
  現在白飯一個框（堆起來的 `mound`），雞肉一個框（平鋪的 `flat`），各自用自己的厚度和密度。
- **回答格式改成兩層**（`gemini_vision.SCHEMA`）：
  - `dishes`：每道菜一筆，六種語言的菜名，加上一句 `recipe`（這道菜通常怎麼做、用什麼油糖醬汁，用頁面語言寫）。
    這是食譜知識，不是照片上看到的。
  - `foods`：每個看得到的食材一筆，各自一個框，`dish_number` 指向它屬於哪道菜；名稱冠上料理方式（照燒雞、白切雞、滷豆腐、白飯）；
    `cooking_method` 依這道菜的食譜判斷，再和看到的對照（照燒＝`sweet_sauce`、白切＝`boiled_or_steamed`、滷＝`braised`）。
- **什麼時候拆、什麼時候不拆**：
  - 盤子上分得開、或疊在上面的就拆：飯和上面的配料、飯上的荷包蛋、旁邊的雞腿、豆腐塊和周圍的醬。
  - 混在一起框不開的維持一筆，用 `components` 寫比例：炒飯、炒絲類、肉燥。
  - **碗和杯子維持一筆**（湯、湯麵、飲料）：裡面是疊起來的，只能用碗的容積估，拆框不會比較準。
- **KEY RULE**：食譜只用來解釋料理方式（看不到的油和糖），不會變成照片證據；指示裡明寫不能因為食譜加入照片上看不到的食材（油、糖、吸進去的醬汁）。
- **網頁**：標題列出菜名，下面一塊淡橘色寫每道菜的食譜，標明「料理方式依食譜推測，不是照片上看到的」；份量列表一列一個食材，
  寫出「屬於照燒雞腿飯」。手動加的菜沒有所屬的菜，照舊顯示。
- **評估工具**（`recognition_metrics.predicted_dishes`）：標註是一道道菜，所以同一道菜的食材會合回一道（菜名、包住所有食材的框、
  所有食材鍵）再比對；舊格式（一道菜一筆）的答案照舊讀。
- **驗證**：用純灰色的假圖片打真的 API，確認 Gemini 接受新的格式（3.5 Flash Lite，4.7 秒）；網頁版面用假答案在 headless Chrome
  看過桌面和手機寬度。**還沒有用真的餐點照片看過 Gemini 實際怎麼拆**，要使用者自己在網頁上試。
- **順便修正**：灰圖片測試時備註回了簡體字，指示加上「中文一律用台灣的繁體字」。
