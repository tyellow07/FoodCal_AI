## 5. MVP 功能完成度（10 分）

四階段（辨識 → 視覺食材證據 → 份量 → 營養）各評等級，加總（滿 16）× 10/16，取到 0.5 分。

| 等級 | 定義 |
| --- | --- |
| L0 | 沒有 |
| L1 | 只有規格或契約 |
| L2 | 合成資料上跑得通，且有自動測試 |
| L3 | 真實照片在網頁或工具上跑得通（非合成） |
| L4 | 在凍結的測試集上量測並公布指標 |

## 7. 隱私、安全與資料授權（5 分，每條 1 分）

1. 上傳照片預設不存檔，並移除 EXIF（含 GPS）。
2. Repo 裡沒有權重、私人照片、秤重資料、API key、TFDA 原始檔（白名單＋掃描）。
3. 每份資料集、權重、TFDA 資料都有來源與授權紀錄（含 TFDA 條款核對者）。
4. 服務預設只在本機；對外開放必須有存取控制。使用雲端辨識（Gemini 免費 API）時，照片只在使用者勾選同意後送出，只送去掉拍攝資訊的縮圖，學生證先塗掉，並告知免費版條款。
5. 結果頁寫明「估計值僅供參考，不是醫療或營養建議」。

## 8. 展示與報告（5 分）

| 子項 | 條件 | 給分 |
| --- | --- | --- |
| 8a Live demo（2） | 用真實照片完成易用性任務 T1–T3，不當機 | 2 或 0 |
| 8b 報告內容（2） | 測試集規模與協定、各項指標數字、≥ 3 個失敗案例與原因 | 2；缺一項 1 |
| 8c 限制說明（1） | 說清楚為什麼食譜候選不是視覺證據，以及目前限制 | 1 或 0 |

建議 3 分鐘展示流程：① 上傳一張校園餐照片（T1）→ ② 讀結果摘要，說明為什麼目前不給熱量（T2、T3）→
③ 打開「這個模型認得哪些食物？」說明類別限制 → ④ 播放已記錄的校園餐流程輸出：有標註、校準、複核的那一餐算出熱量區間，
其他餐列出原因 → ⑤ 秀評分輸出（`evaluate_meals`、`evaluate_stages`、紅線稽核為空）→ ⑥ 一句話說明核心原則。
